**结论：当前“修—验”方式不能可靠收敛。根因是修改没有绑定唯一交付物、事实没有绑定原始证据、“完成”没有绑定独立验收。** 审查发现的问题在积累，已修复的成果却没有被可靠保住。

按你列出的历次记录，三个层面的根因如下：

- **流程层：以局部段落为修改单位，缺少整份交付物的变更控制。** 摘要、正文、总结、附件分别维护同一主张，修改一处不会触发其他位置的检查；重复目录、旧稿、新稿没有唯一身份。每轮只围绕上一轮问题修补，缺少固定的全量验收标准。AI 重写附件时还能顺带增加主张，修复范围因此不断扩大。
- **责任层：执行、汇报、验收之间没有明确交接。** “我改了”“生成完成”可以直接升级成“已完工”，没人必须证明指定文件中的指定问题已经消失。事实来源、修改落盘、整包一致性也没有分别落实到责任人。指定一人终检有用，但必须给他实际交付物、明确标准和退回权。
- **核验层：检查对象和检查深度都不够。** 文件存在不代表有内容，非零字节不代表是新版，正文正确不代表附件正确，自报 PASS 不代表验收通过。事实核验又缺少来源与结论强度的约束，导致 `null` 被补成许可证、怀疑被写成官方确认、两个样本被推广成通常情况。

“生成时为了显得完整”是合理解释，但无法仅凭这些结果确定模型的动机。可以确定的是：**流程允许生成模型填补未知信息，并把生成的分析附件当成了事实依据。** 换模型无法消除这个入口。

要让它收敛，必须先做三项结构性改变：

1. **确定唯一交付版本。** 一个明确目录、一份文件清单、一套版本标识；每个文件同时只允许一个修改者。所有审查意见都绑定具体版本，禁止对着旧版验收新版。
2. **建立“主张—证据—出现位置”表。** 每条事实有稳定 ID，记录原始来源、定位、观察值、适用范围、允许的结论强度，以及摘要、正文、附件中的全部引用位置。同一事实的不同表述都受这条记录约束。
3. **把终检改成真正的验收关口。** 修改者只能报“已修改，待验收”；终检人直接打开实际文件、复核证据、检查关联位置，然后才能关闭问题。终检人自己的修改也需要另一人核验。

**“冻结附件、只改索引”有条件成立。** 原始取证材料可以立即冻结；已有错误的 AI 分析附件必须先更正或撤出本次交付，再冻结。索引无法消除附件中的错误断言。缺证据的主张应降级为未知或撤回，不能靠继续生成附件补齐。

下面这份清单可直接作为验收门禁：

| 检查项 | 可检查的通过条件 |
|---|---|
| **唯一交付清单** | 列出每个交付文件的绝对路径、用途、版本、字节数、哈希；验收和打包都只读取清单中的文件。旧稿与重复目录排除在交付范围外。 |
| **改单定位准确** | 每条问题都有稳定 ID、目标文件、原文锚点、预期结果和关联位置。“条目 26”必须同时核对对应 prompt 的原文，不能只凭序号修改。 |
| **修改确实落盘** | 提供实际文件的修改前后差异，并重新读取目标内容确认。需要修改却没有差异，不能报完成；声称“已满足”必须提交当前内容供复核。 |
| **归档确实有效** | 文件非空、格式可读；压缩归档能解包，内部文件清单与交付清单一致。仅创建文件名不算归档。 |
| **事实逐条可追溯** | 每条事实对应原始来源及准确定位。来源是 `null` 就保留缺失状态；“官方确认”必须有官方原文支撑；两个样本不能支撑总体频率判断。 |
| **修改覆盖所有位置** | 每个被修改的主张，都核对其摘要、正文、总结、附件和索引位置。全文检索辅助查遗漏，再逐处判断语义；不能只证明旧关键词消失。 |
| **结论强度一致** | 逐项核对“确认／疑似／未知”和“完整／部分”等状态。存在缺项时，任何位置的“完整”“100%”都必须重新举证或撤回。 |
| **生成内容不能自证** | AI 附件中的每项事实回指原始材料，不能只回指另一个 AI 总结。修复期间禁止无范围限制的整篇重写；任何新增事实主张必须入表核验。 |
| **问题由验收者关闭** | 关闭记录包含实际文件版本、验证方法和结果。修改者的回执只触发验收，不能代替验收；验收者必须亲自读取交付内容。 |
| **验收绑定具体版本** | 验收通过后保存交付清单及哈希，最终提交包再次比对。任何后续修改都使受影响的验收项失效，交付包必须重新确认。 |

本次应先暂停散点修补，收拢唯一交付版本，把已发现的问题和全部事实主张登记完整，再按上述门禁修复、验收。完成状态统一为：

**待修改 → 已修改待验收 → 已验收 → 已封版。**

“已封版”的条件是：阻断问题全部关闭、交付中的主张都有对应证据或明确的未知状态、跨文件口径一致、实际提交包与验收版本相同。未经检查的部分不能进入“已完工”。
