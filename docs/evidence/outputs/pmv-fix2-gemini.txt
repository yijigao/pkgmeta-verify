## 一、Astra rev3 终审 5 个误判修复详情（逐项落盘）

### 1. 同名文件、不同摘要、无证据绑定到同一制品误判 DIGEST_CONFLICT
- **原错误行为**：只要输入具有相同文件名（`artifact_id`）且两边都有摘要，哈希不同时即直接判定为 `DIGEST_CONFLICT`。该逻辑误将“两边都有哈希”等同于“制品级身份证明”，但在无证据证明两份摘要源自同一制品时，仅同名文件无法证明属于同一制品。
- **修复方案**：
  - 在 `Verifier._evaluate_digest_constraints` 中实现 `_check_artifact_identity_provenance` 强约束。
  - 必须具备以下三类制品身份关联证据之一：
    1. **同一下载 URL**：`url` / `download_url` 相同，或一源的 `origin_url` 指向另一源的下载地址；
    2. **同一包内文件清单**：两源具备相同的包内文件清单或 manifest（`file_list` / `files` / `manifest`）；
    3. **同一制品发布记录**：两源显式绑定至同一发布记录（`release_record` / `release_id` / `package_release`）。
  - 若缺乏上述身份关联证据，严禁判定为 `DIGEST_CONFLICT`，强制输出 `category: "INDETERMINATE"`（子状态码 `ARTIFACT_IDENTITY_UNPROVEN`，置信度 1.0）。
- **回归测试**：
  - `test_rev3_fix1_unproven_identity_different_digests_yields_artifact_identity_unproven`：仅同名文件、无关联证据时，验证输出 `ARTIFACT_IDENTITY_UNPROVEN`，拒绝 `DIGEST_CONFLICT`。
  - `test_rev3_fix1_proven_identity_different_digests_yields_digest_conflict`：具备发布记录绑定时，不同摘要正确判定为 `DIGEST_CONFLICT`。

### 2. 两个 Base64 摘要仅大小写不同转小写判匹配
- **原错误行为**：在比对前对摘要执行无差别 `.strip().lower()` 字符串匹配。但 Base64 编码具有严格的大小写区分敏感度（如 `d` 与 `D` 代表完全不同的 6-bit 编码值），将其转为小写破坏了原始摘要含义，导致将不同的 Base64 摘要误判为一致。
- **修复方案**：
  - 引入编码感知解码器 `Verifier._decode_digest_bytes`，对摘要**解码为原始字节（raw bytes）后进行字节比对**；彻底禁止静默 `.lower()` 字符串匹配。
  - 对于十六进制 Hex 编码，经解码后相同字节序列自然匹配，消除单纯大小写表象差异；
  - 对于 Base64 编码，区分大小写解码为真实字节序列，大小写不同的字符串解码出不同字节，真实体现哈希差异；
  - 若摘要编码未知或不支持（如非法的 Base64、或 `base58` 等未知编码），明确输出 `category: "INDETERMINATE"`（子状态码 `ENCODING_UNSUPPORTED`），并在审计轨迹与 details 中详细记录解码失败原因。
- **回归测试**：
  - `test_rev3_fix2_base64_case_difference_does_not_silently_match`：输入仅大小写不同的 Base64 摘要（`dGVzdDE=` vs `DGVzdDE=`），验证解码字节不一致，未被静默判定为匹配。
  - `test_rev3_fix2_unsupported_encoding_yields_encoding_unsupported`：输入不支持的编码（如 `base58`），验证输出 `ENCODING_UNSUPPORTED`。
  - `test_rev3_fix2_hex_case_difference_matches_at_byte_level`：十六进制 Hex 大小写差异在字节层级解码一致并正常匹配。

### 3. 后续观察仍 404、缺时间、时间倒序误判 SYNC_DELAY
- **原错误行为**：在 `_evaluate_sync_delay` 中，只要下游存在 `subsequent_observation` 字段即判定 `SYNC_DELAY`，未校验后续观察是否真正成功（如仍为 404）、后续观察是否具备有效时间戳、以及观测时间戳是否存在时间倒序。
- **修复方案**：
  - 严格要求**三要素同时满足**方可判定 `SYNC_DELAY`：
    1. **HTTP 成功状态**：后续观察 HTTP 状态码必须为成功（`200 <= status < 300`），若仍为 404 或非成功，输出 `undecidable`；
    2. **有效时间戳**：上游发布时间、初始 404 缺失观察时间、后续观察时间三者时间戳均有效且可解析；
    3. **严格正向时间顺序**：必须满足 $t_{observed\_after} > t_{observed\_before} > t_{published}$（即后续观察必须晚于缺失观察，缺失观察必须晚于上游发布时间）；
  - 任一条件不满足，强制输出 `category: "INDETERMINATE"`（子状态码 `undecidable`，疑似延迟，标注不确定性）。
- **回归测试**：
  - `test_rev3_fix3_subsequent_observation_404_yields_undecidable`：后续观察状态码仍为 404 时，拦截 `SYNC_DELAY`，输出 `undecidable`。
  - `test_rev3_fix3_subsequent_observation_missing_time_yields_undecidable`：后续观察缺少时间戳时，拦截 `SYNC_DELAY`，输出 `undecidable`。
  - `test_rev3_fix3_time_inversion_yields_undecidable`：后续观察时间早于缺失观察时间（时间倒序）时，拦截 `SYNC_DELAY`，输出 `undecidable`。

### 4. 两源许可证 MIT vs Apache-2.0，或一源无可比字段误判 CONSISTENT
- **原错误行为**：原一致性判定器 `_evaluate_consistent` 仅检查“是否存在非空数据”而未实际逐字段比对；且 `_evaluate_semantic_divergence` 仅检查了带 `AND`/`OR` 的复合表达式。导致简单的 `MIT` vs `Apache-2.0` 或一源缺少许可证字段时，被直接放行判定为 `CONSISTENT`（“无比较就判一致”）。
- **修复方案**：
  - 在 `_evaluate_semantic_divergence` 中加入通用多源许可证实际比对逻辑：当两源分别声明不同许可证（如 `MIT` vs `Apache-2.0`），明确属于语义不一致，判定为 `category: "SEMANTIC_DIVERGENCE"`（子状态码 `LICENSE_DECLARATION_DISCREPANCY`）；
  - 在 `_evaluate_consistent` 中引入**可比字段完备性核验**：若一源提供许可证元数据而另一可用源缺少可比许可证字段，严禁默认一致，强制输出 `category: "INDETERMINATE"`（子状态码 `undecidable`，details 标明缺少可比字段）；
  - 只有在至少 2 个可用源均提供可比字段且全部比对通过时，方可输出 `CONSISTENT`。
- **回归测试**：
  - `test_rev3_fix4_mit_vs_apache_yields_semantic_divergence_not_consistent`：验证 `MIT` vs `Apache-2.0` 判定为 `SEMANTIC_DIVERGENCE`，严禁判定为 `CONSISTENT`。
  - `test_rev3_fix4_missing_comparable_license_field_yields_undecidable`：验证一源声明许可证而另一源为空时输出 `undecidable`，拒绝默认一致。
  - `test_rev3_fix4_matching_licenses_across_sources_yields_consistent`：验证可比字段均存在且一致时正常输出 `CONSISTENT`。

### 5. 未提供制品 LICENSE 原文误判 REAL_ERROR 且硬编码 PSF 许可证断言
- **原错误行为**：当 `deps.dev` 报告 `non-standard` 时，代码在 details 中写死“`The artifact dist-info/LICENSE contains the standard Python Software Foundation License Version 2.`”，即使输入数据中根本没有提供制品 LICENSE 文本证据也直接下此断言并判定 `REAL_ERROR`。
- **修复方案**：
  - **删除一切硬编码事实断言**；
  - 强制核验 `license_text_evidence` 及其 `text_snippet` 经验证据；若未提供对应经验证据，严禁判定 `REAL_ERROR`，强制输出 `category: "INDETERMINATE"`（子状态码 `undecidable`，标明缺乏经验证据）；
  - 当且仅当提供制品 LICENSE 原文证据时，方可判定 `REAL_ERROR`，且 details 必须动态提取证据中的文件名与许可证标识（如 `The artifact {file_name} contains verified license text ({spdx_id})`），彻底杜绝无证据的事实断言。
- **回归测试**：
  - `test_rev3_fix5_missing_artifact_license_text_yields_undecidable_not_real_error`：未提供制品 LICENSE 文本证据时，验证拦截 `REAL_ERROR`，输出 `undecidable`，且 details 中绝无硬编码断言。
  - `test_rev3_fix5_provided_artifact_license_text_yields_real_error_dynamically`：提供制品文本证据时，动态生成事实依据并输出 `REAL_ERROR`。
