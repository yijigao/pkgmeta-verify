- **申请人／技术负责人**：Joey（Jigao Yi），个人申请，负责开发、验证、交付与上游沟通。
- **申请金额**：€15,000。
- **范围**：npm＋PyPI 两个生态；跨源判定、时间追踪、离线复现三项核心能力。
- **周期**：9 个月计划交付，12 个月内完成约定验收返修。
- **评审组织**：相关性与影响 40%、技术可行性 30%、性价比 30%；分别用接入场景、实测证据与净额任务估时支撑。[申请指南](https://nlnet.nl/codesupply/guideforapplicants/)

## 2. 问题、定位与预期价值

### 2.1 问题陈述

- 聚合方面对同一版本的许可证、仓库链接、发布时间、制品摘要及生命周期信息时，需要区分字段错误、疑似同步延迟、语义差异与证据不足。
- 字符串 diff 无法充分表达来源依赖、比较范围和时间口径，也不能解释为何得出某一判定。
- 已有来源记录、证明验证与修订机制可作为输入；PMV 提供统一的跨源判定及可复跑证据包。

### 2.2 项目定位

- 消费官方 API、聚合方提供的记录及固定快照；采集限于校验所需证据。
- 提供 CLI、Python 库与版本化 JSON Schema。
- 输出字段级判定、时间观察记录和最小证据包。
- 接入位置拟定为：**数据摄取后、聚合记录发布前**，或作为既有数据集的批量审查步骤；具体接口通过上游 issue 对齐。
- 当前不承诺零改造接入，接入成本以实际适配示例验证。

### 2.3 增量边界

1. **跨源判定**：记录原始值、来源依赖、可比条件、规则及判定理由。
2. **时间追踪**：分别记录抓取时间、上游发布时间、索引时间与观察时间，追踪差异持续和消失过程。
3. **离线复现**：固定最小证据快照、规则、软件版本及运行参数，复算同一结果。

坐标解析复用 PURL 标准；漏洞信息与依赖图复用已有系统。

## 3. 相关项目与差异

| 项目 | 已有能力与应承认的基础 | PMV 的具体关系 |
|---|---|---|
| CodeSupply／AboutCode／PurlDB | 软件供应链元数据采集、组织与聚合基础 | 对齐具体输入输出接口，补充跨源判定、时间观察与离线证据包 |
| purl-validator／PURL 测试集 | 坐标存在性检查及解析、归一化测试基础 | 复用适用结果和测试集；增加版本与字段级证据判定 |
| ClearlyDefined | declared／discovered 许可证信息、原始采集记录、工具输出与修订机制 | 保留其分析范围及修订来源，与注册表声明作显式比较。[架构说明](https://docs.clearlydefined.io/docs/resources/architecture) |
| deps.dev | 包版本、许可证、依赖与来源信息；已有 provenance／attestation 验证信息及问题反馈入口 | 作为对照源，保留其字段语义与注册表依赖；提供项目定义的跨源判定和固定快照复算。[API 文档](https://docs.deps.dev/api/v3/) |
| OSV | 漏洞记录、受影响版本范围及漏洞数据处理基础 | 本轮不承担漏洞归一，也不以 OSV 证明包撤回或改名 |

差异论证只围绕三项核心能力，不以其他项目缺少所有 provenance、无法反馈问题或质量评分低作为依据。

## 4. 双生态来源与依赖关系

| 生态 | 最低来源组合 | 补充来源 |
|---|---|---|
| npm | npm registry＋deps.dev | ClearlyDefined 许可证字段 |
| PyPI | PyPI＋deps.dev | ClearlyDefined 许可证字段 |

- PyPI JSON 与 Simple 是同一注册表的两个接口，分别记录接口，不能计为两个独立真值来源。
- deps.dev 部分字段摄取自注册表；来源一致可能只是传播一致，不能自动当成独立证明。[数据说明](https://docs.deps.dev/api/v3/#data)
- ClearlyDefined 的包制品来源、扫描工具、扫描范围及人工修订信息按可获得程度记录；未知依赖明确标为未知。
- 来源依赖尽量记录到字段层，避免把整个服务一概认定为独立或从属。
- 不使用 OSV `withdrawn` 判断包撤回、改名或迁移；该字段表示漏洞记录撤回。

### 5.3 四类真实案例提交门槛

- **真实错误**：补齐足以证明具体字段错误的原始材料；不能用不同分析范围直接证明某源错误。
- **同步延迟**：保存真实上游发布时间、带时间戳的缺失观察，以及后续摄取成功记录；仍无法解释的差异保留不确定性。
- **语义差异**：保留 esprima 的真实快照及字段范围说明。
- **不可判定**：补至少一个自然发生的证据不足或不可比案例；构造输入单独统计。
- 四类各至少一个真实实测案例，均附包名、版本、PURL、endpoint、状态、时间、快照哈希、规则及理由。

## 6. 判定规则与输出契约

### 6.1 判定类别

| 判定 | 必要条件与边界 |
|---|---|
| `real_error` | 有可复核证据证明具体字段错误，明确比较范围与责任边界 |
| `sync_delay` | 有时间证据支持延迟解释；疑似状态单独标注，不能把抓取时间当发布时间 |
| `semantic_diff` | 字段定义、分析范围或表达式不同；不自动认定双方都对 |
| `undecidable` | 缺证、来源不可用、跨算法、不同制品或其他不可比情况，附原因码 |
| `digest_conflict` | 已满足同一制品、同一算法、编码归一条件，摘要仍不同；不推断损坏或篡改 |
| `consistent` | 仅在已检查字段与比较范围内一致，不宣称全包正确 |

### 6.2 硬约束

- 制品逐文件比较，区分 wheel、sdist、npm tarball；同名文件不足以独立证明内容身份。
- 同算法摘要先规范化编码，保留原始值；base64 内容不能通过统一小写处理。
- 跨算法、跨制品及比较证据不足统一返回 `undecidable`，不因不可比中断整批任务。
- AND／OR 表达式保留逻辑结构与适用范围；只有规则与证据明确支持时才转换。
- 明确区分 `fetched_at`、`published_at`、`indexed_at`、`first_seen_at`。
- 时间缺失时不计算虚构延迟；超过观察窗口也不自动证明永久缺失。
- 未校准的原型 confidence 数值不作为正确率或概率宣传。

### 6.3 输入输出

- **输入**：带版本 PURL 列表、来源配置、固定快照、版本化规则。
- **判定输出**：`purl`、版本、字段／制品、原始值、归一值、类别、原因码、规则版本、证据引用、来源依赖及时间字段。
- **生命周期输出**：明确的 yanked／deprecated 状态、观察到的可见性变化，以及有公告、重定向或维护者声明支持的改名迁移事件。
- **错误处理**：网络失败与字段缺失明确记录，不因默认分支自动输出一致。
- **接入策略**：疑似延迟进入重查队列；语义差异进入复核；不可判定保留缺证状态；真实错误与摘要冲突按聚合方策略处理。

## 7. 可计量交付范围

### 7.1 数据集规模与观察周期

- M1 小样：**200 个唯一版本坐标**，npm／PyPI 各 100；构造测试不计入真实样本。
- 正式 dataset v1：**1,000 个唯一版本坐标**，两生态各 500，公开采样清单与分层依据。
- 每个坐标至少进行 **3 次观察，跨越不少于 30 天**；目标至少 3,000 个坐标观察记录。
- 每轮覆盖注册表＋deps.dev；请求失败仍保存状态。ClearlyDefined 用于许可证补充，披露实际覆盖率。
- 在正式样本中选 **100 个坐标**进行连续 30 天每日观察，用于差异持续时间与恢复记录。

### 7.2 覆盖字段

PURL／名称／版本、版本可见性、许可证声明与表达式、仓库链接、发布时间、制品 URL／类型／大小／摘要，以及来源可提供的 yank／deprecated 信息。

缺字段不补造；分别报告可获得率、可比较率和不可判定率。

### 7.3 离线复现包

包含最小可再分发证据快照、字段裁剪说明、来源及许可、规则文件、Schema、代码版本、运行参数、基线输出、复跑命令、日志与 `MANIFEST.sha256`。

- 结果数据拟采用 CC-BY-4.0；代码采用 Apache-2.0。
- 来源快照保留原有许可与署名要求，逐项核查再分发条件。
- 不可再分发证据不得作为公开离线验收的唯一输入。
- 评分卡报告覆盖率、冲突率、不可判定率、差异持续时间及有证据支持的延迟；缺少更新时间的数据不计算“陈旧率”。
