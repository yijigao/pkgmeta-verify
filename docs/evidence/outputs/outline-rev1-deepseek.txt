## 2.1 项目标题与定位

> **Package Metadata Verifier（PMV）——可接入 CodeSupply 聚合管线的独立质检组件：带来源、时间与可复现证据的跨源包元数据差异判定与生命周期追踪**

**一句话定位**：本项目**不采集、不聚合、不重建数据集**；它消费各权威源已经发布的包元数据，做**带 provenance 与时间戳的跨源差异判定和生命周期追踪**，输出机器可读、可离线复现、可整包下载的**校验结论**，供任何聚合方（含 CodeSupply 核心聚合管线）作为第三方质检组件接入。

**明确定位为"组件"的三个含义**：
1. **可接入**：提供 CLI + 稳定 JSON Schema 的库，聚合方按 `purl + version` join 即可消费判定结果，无需改其内部架构。
2. **独立**：不写上游、不依赖任何闭源服务、无密钥、支持离线快照回退；即使不接 deps.dev / ClearlyDefined 也可完整运行。
3. **质检而非重建**：只补"对不对、还新不新、谁在何时说过"，不重做采集/归一/漏洞/依赖图。

## 2.2 定位与接入方式：输入 / 输出 / 接入示例

### 2.2.1 输入（吃什么格式）

1. **待校验坐标表** `coords.jsonl`（或 `purls.txt`），每行一个：
   - `{"purl":"pkg:npm/lodash@4.17.21"}`
   - `pkg:pypi/requests@2.31.0`
   - 允许只给包名（则枚举该包所有版本做存在性与生命周期判定）。
2. **源适配器配置** `sources.yaml`：每源声明 `id、ecosystem、endpoint 模板、认证（默认 none）、限速、快照目录、数据许可`。
   - 本轮锁定 **npm**：npm registry 官方接口 ＋ deps.dev API（ClearlyDefined API 作可选第三源）。
   - 本轮锁定 **PyPI**：PyPI JSON API / Simple index ＋ deps.dev API（ClearlyDefined / OSV export 用于生命周期交叉核对）。
3. **固定输入快照** `snapshots/<source_id>/<fetched_at>/…`：抓取结果原样落盘，附 `_meta`（`source_id、url、http_status、etag/last-modified、snapshot_sha256、fetched_at、抓取工具版本`）。**判定阶段只读快照，不依赖实时网络**——这是"可复现"的物理前提。
4. **版本化规则文件** `rules/normalization-v1.yaml`、`rules/verification-v1.yaml`：含归一化规则、判定阈值、权威源优先级、**哈希比较硬约束**、判定类别映射。规则文件本身可测试、可引用、带版本号。

### 2.2.2 输出（产出什么）

| 产物 | 格式 | 内容要点 |
|---|---|---|
| `out/discrepancies.jsonl` | JSON Lines，每行一个 (坐标, 字段, 判定类) | `purl、version、field、verdict∈{real_error, sync_delay, semantic_diff, undecidable, consistent}、sources[]{source_id,endpoint,fetched_at,snapshot_sha256,value}、rule_id、rule_version、checked_at、evidence` |
| `out/lifecycle.jsonl` | JSON Lines | 存在性、撤包/yank、改名/迁移事件，带 `first_seen_at / last_seen_at / source_id / evidence` |
| `out/scorecard.json` | JSON | 每生态/每源的覆盖率、冲突率、陈旧率、不可判定率；作为时间序列发布 |
| `out/dataset-<version>.tar.zst` | 压缩包 | 正式校验结果数据集；附 `MANIFEST.sha256`（可选 Sigstore 签名）与 `CITATION.cff`；许可 CC-BY-4.0；可整包离线下载 |
| `out/report.html` / `out/report.sarif` | HTML（WCAG 2.2 AA）/ SARIF 2.1.0 | 人类可读报告；SARIF 供 CI 消费；CLI 另提供纯文本、非颜色依赖输出 |

### 2.2.3 接入示例（聚合方如何调用）

**CLI 示例**：

```bash
pkgmeta-verify verify \
  --coords coords.jsonl \
  --sources sources.yaml \
  --snapshots ./snapshots \
  --rules ./rules \
  --out ./out \
  --format jsonl,sarif
```

**库调用示例**（Python 包，稳定 JSON Schema）：

```python
from pkgmeta_verify import Verifier
v = Verifier(sources="sources.yaml", rules="rules/", mode="offline")
records = v.verify(coords)   # -> {"discrepancies": [...], "lifecycle": [...]}
```

**聚合方接入契约**（写进提案，避免厂商锁定）：

1. 以 `purl + version` 为联合键 join 聚合记录；校验器**只读、不修改上游源数据**。
2. 判定到策略的默认映射：`real_error` → 隔离/告警；`sync_delay` → 按 `retry_after` 重查；`semantic_diff` → 套用 `rule_id` 规范化并保留原始值；`undecidable` → 降置信度、人工/智能体复核；`consistent` → 放行。
3. **CI 集成**：提供 conformance kit 与 GitHub Action 示例，用固定快照离线复跑，出现新的 `real_error` 时非零退出。
4. **接入成本趋零**：无密钥、无云账号、可完全离线；离线快照回退保证上游宕机时仍可复算。

## 2.3 问题陈述（对应 40% 相关性/影响）

现有项目解决了"**有没有**"（AboutCode/PurlDB、ClearlyDefined、deps.dev 都在采集）和"**漏没漏**"（OSV 做漏洞），但没有解决"**对不对、还新不新、谁在何时说过**"：

- 同一 PURL 在不同权威源之间的字段会互相矛盾（许可证声明、仓库链接、发布时间、生态归属），且**没有任何一处带来源与时间地判定谁错、谁只是慢、谁只是口径不同**。
- ClearlyDefined 官方明确"**不解决 identity 问题**"，且**无独立校验层**；`licensedScoreMedian` 仅 60，数据陈旧。
- AboutCode `purl-validator` 目前**只判 base PURL 是否存在**，不校验版本存在性、撤包、改名、哈希漂移。
- deps.dev **后端闭源、不接受外部校验**，缺撤包/改名/维护者字段，全量数据只能走 BigQuery。
- **PURL 官方测试集**只覆盖 PURL 字符串规范化一致性，不涉及跨源元数据比对。
- OSV 的质量校验只在**导入期、面向 advisory**，不是包级。

结果是：CodeSupply 这类聚合即使成功，**下游拿到的仍是"未经验证、无 provenance 的元数据"**；CRA 等要求"可验证、可追溯"的场景下，冲突与过期数据无人负责。**我们只补这一层。**

## 2.4 增量聚焦（唯一主张）

> **唯一主张：带来源、时间和可复现证据的跨源差异判定与生命周期追踪。**

**明确剔除（不算创新，仅作基线接入与测试基础设施）**：

- ❌ 普通**存在性检查**——AboutCode `purl-validator` 已有 base PURL 存在性校验，我们直接接入其结果并向下扩展到版本级与字段级，不主张存在性本身是创新。
- ❌ **PURL 归一化测试**——PURL 官方已有 conformance 测试集；我们的边界语料只用于保证自身判定正确，不计入创新主张。
- ❌ 坐标/标识归一、依赖图解析、漏洞归一、联邦数据目录——全部不做。

**本增量必须同时满足三要素，缺一不算**：

1. **来源（provenance）**：每条判定都能追到 `source_id + endpoint + fetched_at + snapshot_sha256`。
2. **时间**：判定能区分"错误"与"时间差"，并显式解释同步延迟，而不是把新旧快照一律当冲突。
3. **可复现证据**：固定输入快照 + 固定规则版本 → 逐字节可复算同一判定。

## 2.6 真实冲突样例设计

### 2.6.1 判定类别定义

| 判定 | 定义 | 必要条件 |
|---|---|---|
| `real_error` | 有权威、可复核证据证明某一源字段错误，或同一制品完整性不一致 | 存在权威源/内部一致性反证；证据可离线复算 |
| `sync_delay` | 差异可被采集时间差**完全解释** | 较新源的发布时间晚于较旧快照的生成时间；记录双方时间 |
| `semantic_diff` | 差异源于字段语义/归一化口径不同，双方表述各自成立 | 引用具体归一化规则；处理后可能一致或属于不同但都对 |
| `undecidable` | 证据不足或不可比 | 输出 `unknown` + 原因码；**绝不猜测、绝不误报 mismatch** |
| `consistent` | 多源一致 | 正样本，用于计算覆盖率与正确率 |

**每条判定必须携带 provenance（source_id/endpoint/fetched_at/snapshot_sha256）与时间口径**，否则降级为 `undecidable`。

### 2.6.2 样例表（≥4 类，含哈希例）

> 以下为**真实机制的样例设计**；具体包名/版本在 M1 用实时抓取固化并写进 conformance kit，提案中不点名任何未经复核的项目。

| 编号 | 类别 | 生态/对象 | 冲突机制（真实成因） | 来源与时间口径 | 期望判定 | 判定依据/规则 |
|---|---|---|---|---|---|---|
| S1 | **真实错误** | npm，版本级发布时间 | 某聚合快照把包级 `modified` 时间**复制到所有版本**，导致历史版本发布时间整体错误；registry packument 的 `time` 有逐版本权威时间 | 源 A：npm registry（权威，`time["<v>"]`）；源 B：某数据集快照 | `real_error`（指向源 B 的 `publishedAt`） | 权威源优先级 + 内部一致性反证（源 B 所有版本时间戳完全相同＝异常模式） |
| S2 | **同步延迟** | npm 或 PyPI，新发布版本 | 版本刚发布数小时；registry 已列出，日更数据集尚未含该版本 | 源 A：registry（`fetched_at` 为 T）；源 B：数据集快照（`built_at` < T 且早于发布时间） | `sync_delay`（pending，非冲突）；给出 `retry_after` | 时间先后关系：`snapshot_built_at < version_published_at ≤ source_a_fetched_at` |
| S3 | **语义差异** | PyPI，许可证字段 | PyPI `info.license` 是自由文本（"MIT License" / "MIT" / "UNKNOWN"），deps.dev/ClearlyDefined 用 SPDX；ClearlyDefined 还区分 declared/discovered | 源 A：PyPI JSON；源 B：deps.dev/ClearlyDefined | `semantic_diff`；规范化后可能升为 `consistent` | 套 SPDX 归一规则（`rule_id=license-spdx`）；表达式 OR/AND 不同则保留语义差异，不判错误 |
| S4 | **语义差异**（归一化） | PyPI / npm，名称与版本 | PyPI 名称 PEP 503（大小写/`.`/`_`/`-`）、版本 PEP 440（`1.0`≡`1.0.0`、`1.0.post1`）；npm 名称强制小写 | 双方各自命名 | `semantic_diff` → 归一后 `consistent` | 归一规则显式化；若源使用了非规范写法，记 note 而非 error |
| S5 | **无法判定** | npm / PyPI | 该字段仅一个源提供；或哈希仅单源；或仅剩不同算法的哈希；或依赖的快照已不可获取 | 单源或不可比 | `undecidable`（`unknown` + 原因码 `single_source` / `no_common_algorithm` / `evidence_expired`） | 不可比即如实标注；**禁止**用启发式猜出 mismatch |
| S6 | **真实错误**（哈希） | npm / PyPI，同一制品 | 同一制品（同文件名+同大小）、**同一算法**（均 sha256）的两个来源摘要不同 → 镜像损坏或篡改 | 源 A：registry；源 B：镜像/数据集 | `real_error`（integrity） | 仅当"同一制品 + 同一算法"成立；否则不进入本判定 |

### 2.6.3 哈希比较硬约束（写进校验规则）

写入 `rules/verification-v1.yaml`，违反即**硬失败报错**，绝不输出判定：

1. **同一制品**：`ecosystem/namespace/name/version` 相同，且分发文件名（及大小，若可用）相同；sdist 与 wheel 视为不同制品。
2. **同一算法**：算法标识完全相同（sha256 vs sha256）。编码差异（hex / base64 / `sha512-` 前缀）**先规范化编码再比较**；编码不同不等于算法不同。
3. **跨算法一律不可比**：如 npm `dist.shasum`（sha1, hex）vs `dist.integrity`（sha512, base64）→ `not_comparable`，**绝不判 mismatch**。
4. **多文件版本按文件逐一比较**，禁止把多个分发文件折叠成单一"版本哈希"。
5. 任何违反上述约束的比较尝试 → 校验器报错退出（非零），而不是静默降级。

## 2.7 技术路线（对应 30% 技术可行性；本轮锁定 2 个生态）

关键澄清：此处"采集"**不是**重建 registry 爬虫，而是**采集上游既有元数据与校验证据**；"归一"**不是**重做坐标模型，而是**把不同源的同一坐标对齐到可比较的字段集**；重心在"**校验**"。**本轮锁定 npm + PyPI，每生态 ≥2 个对照源，不设"扩至第 5–6 生态"的承诺。**

- **P1（T+0 → T+3）：对齐层 + 端到端核心校验**
  - 锁定 npm + PyPI；每生态 ≥2 对照源（registry 官方接口 + deps.dev；ClearlyDefined/OSV 作可选交叉源）。
  - 定义统一 `SourceRecord` schema 与 `_meta` provenance；落地快照抓取与离线加载。
  - 接入 PURL 官方测试集与 `purl-validator` 结果作为**基线**（非创新）。
  - 跑通**端到端最小闭环**：坐标 → 快照 → 对齐 → 四类判定 → **可下载的小样结果集**（含每类样例 ≥2，总坐标数约 200–500）。
  - 交付：`pkgmeta-verify` v0.1（CLI + 库）、CI 绿、覆盖率门槛、归一规则文件 v1 冻结、小样结果集（带 SHA-256 清单）。
