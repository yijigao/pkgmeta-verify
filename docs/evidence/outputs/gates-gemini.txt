## 二、逐项证据核验与分析报告

### 1. 真实错误案例最终确认 (`typing-extensions@4.12.2`)

#### (1) 原始证据链
- **制品许可证原文**:
  - 制品文件：`typing_extensions-4.12.2-py3-none-any.whl`（SHA-256: `269fad63fc0248c5379346306f8668cda6e2e2e9c95e01216d2b8ffd9ff037d0`）
  - 内置路径：`typing_extensions-4.12.2.dist-info/LICENSE`
  - 原文为完整的标准 `PYTHON SOFTWARE FOUNDATION LICENSE VERSION 2`，对应 SPDX 标识符 `PSF-2.0`（或 `Python-2.0.1`）。
- **上游发布元数据规范 (PyPI Core Metadata)**:
  - 源码 `pyproject.toml` 采用 PEP 621 语法 `license = { file = "LICENSE" }` 与 Trove 分类器 `Classifier: License :: OSI Approved :: Python Software Foundation License`；
  - `flit_core` 打包生成的 `METADATA` (Metadata-Version 2.1) 未生成 `License:` 文本标头（当时 PEP 639 尚未普遍强制落地），PyPI JSON API 忠实反映为 `info.license: null`。
- **下游衍生索引规范 ([deps.dev FAQ](https://docs.deps.dev/faq/#how-are-licenses-determined) 与 [Issue #94 维护者回复](https://github.com/google/deps.dev/issues/94))**:
  - deps.dev 明确指出仅解析 wheel 的 `METADATA` 中的 `License:` 文本标头，且因历史歧义原因明确**不采信 Trove Classifiers**；在未映射到 SPDX 表达式时，按公开策略回退为 `licenses: ["non-standard"]`。
- **辅助分析**: ClearlyDefined API 深度分析返回 `declared: "Python-2.0.1"`。

#### (2) 区分“字段错误” vs “解析器故障”的因果判定
- **能否证明上游“字段错误”？** 不能。上游开发者完全遵循当时的 PEP 517/566/621 标准与 Trove 分类器生态规范，没有违反任何打包约束，无法定性为字段填写错误；
- **能否证明下游“解析器故障”？** 不能。deps.dev 严格执行了其公开声明的降级策略（无显式 SPDX 标头即输出 `non-standard`），程序没有崩溃、无反序列化异常；
- **本质诊断**: 该差异是 **Python 打包生态历史标准（文件表+分类器）与外部现代索引器（强制要求单一 SPDX 标头）之间的标准脱节与语义阻抗（Standards/Semantic Mismatch）**。

#### (3) 处理落实
- **彻底删除 `DOWNSTREAM_PARSING_ERROR` 单边责任断言**：在 PMV 规则引擎中已彻底删除该子状态码，客观以 `STANDARDS_CONTRADICTION` 记录跨标准冲突，避免合规系统误拒核心基础库；
- **换案例方案**：在 `evidence/real-error-case.md` 中记录了若后续严格审查要求 100% 封闭的“纯语法/格式字段错误”，推荐替换为违反 SPDX 语法的真实 npm 案例（如 package.json 声明非法表达式）。

#### (3) 为什么不可比 (Why Incomparable)
- **触发硬约束规则**: `CONSISTENCY_01_COMPARABLE_LICENSE`（`has_comparable_license_declarations == False`）；
- **判定输出**: `category: INDETERMINATE`，`subcode: undecidable`，`confidence: 0.0`；
- **形式化逻辑证明**:
  各对照源均未提供任何实质性的许可证声明。“双源皆空（`null == null`）”在形式逻辑上**仅代表双方共同缺失证据（Evidence Vacuum），绝不能等同于“已验证一致（CONSISTENT）”**。在缺乏可比对的实质元数据事实的前提下，跨源一致性在逻辑上属于典型的**自然不可判定**。
- **相较普通 Diff 避免的误判**:
  避免传统 Diff 工具因 `null == null` 机械判断为 PASS，误向合规系统报告“经核验证实一致”，导致下游系统放行版权完全保留、零授权保护的高风险代码。
